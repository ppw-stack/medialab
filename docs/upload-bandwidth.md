# 数据同步上传的带宽瓶颈（2026-11-02 实测结论）

**一句话结论**：光鸭上传速率受限于**本机上行带宽（~3 MB/s）**，
不是代码实现问题。并发上传（分片并发 / 文件并发）**换不来吞吐**，
反而会让服务端不稳定。当前实现**只能串行**。

本文记录实测数据与走过的弯路，避免以后重复踩。

## 背景

「同步刮削」任务把本地影视文件（1-1.7 GB/个）传到光鸭盘。
观察到的现象：单文件要传 5-11 分钟，速率稳定在 ~3.3 MB/s。
总剩余量数百 GB → 需要数十小时。

问题：**能不能提速？**

## 实测环境

| 项 | 值 |
|---|---|
| 客户端 | prod 容器（`ssh mp`，192.168.0.128） |
| 网盘 | 光鸭（`guangya`），真实账号 |
| OSS endpoint | `cn-zhangjiakou.oss.aliyuncs.com`（阿里云张家口） |
| RTT | **31 ms** |
| 分片大小 | 5 MB（`CHUNK_SIZE`） |

## 关键数据

### 1. 本机上行基线

```
本机 → speed.cloudflare.com:  3.2 MB/s
```

### 2. 本机 → 光鸭 OSS

| 分片方式 | 耗时（100MB） | 速率 |
|---|---|---|
| 1 片 × 100MB（单 PUT） | 36.4s | 2.75 MB/s |
| 20 片 × 5MB（生产方式） | 44.4s | 2.25 MB/s |
| 5 片 × 20MB | 43.8s | 2.28 MB/s |

**与本机上行 3.2 MB/s 基本吻合** → 瓶颈是本机上行，不是光鸭。

### 3. 分片大小几乎不影响速率

1 片 / 5 片 / 20 片都是 2.25-2.75 MB/s。

**这是「带宽受限」而非「RTT 受限」的决定性证据**——若是 RTT 受限，
大分片（请求数少、RTT 少）会明显更快。

### 4. 并发实测（全部无收益或更差）

**同一 uploadId 的分片并发**

| 场景 | 结果 |
|---|---|
| 100MB / 20片，串行 | 21.08s（4.74 MB/s） |
| 100MB / 20片，并发 2 | 21.32s（4.69 MB/s）——**零收益** |
| 100MB / 20片，并发 4 | 21.14s（4.73 MB/s）——**零收益** |
| 200MB / 40片，并发 4 | ❌ 卡死（>90s 无响应） |
| 纯串行 4 轮 | 24.28 / 26.89 / 25.70 / 17.08s ← 稳定 |

**不同 uploadId 的并发**（= 文件级并发）

| 场景 | 结果 |
|---|---|
| 60MB × 4，并发 4 | ❌ `Server disconnected without sending a response` |
| 20MB × 4，并发 2 | ❌ 卡死 |
| 30MB × 2，并发 2 | ok，但总吞吐 2.40 MB/s |
| 60MB × 2，并发 2 | ok（3 轮），总吞吐 2.26~2.43 MB/s |

**严格对照**（60MB × 2，生产分片路径，交替跑）

| 模式 | 耗时 | 总吞吐 |
|---|---|---|
| 串行 | 36.8s | **3.26 MB/s** |
| 并发 2 | 66.8s | 1.80 MB/s（**比串行慢 45%**） |
| 串行 | 62.1s | 1.93 MB/s |
| 并发 2 | 48.4s | 2.48 MB/s |

并发**不稳定优于串行**，且波动极大。

### 5. 唯一支持并发的是小文件单 PUT

| 场景 | 结果 |
|---|---|
| 1MB × 6，并发 6（单 PUT，不分片） | ok=6 err=0，1.48x 加速 |
| 20MB 单片 × 2，并发 2 | 3.17 MB/s（接近翻倍） |
| 20MB 单片 × 4，并发 4 | ❌ 卡死 |

但小文件本来就不是瓶颈（一个 nfo 传 2-4 秒），且 ≥3 并发就会卡死。

## 走过的弯路（方法论教训）

### 教训一：小样本测试在带宽受限的系统上会给出完全错误的结论

第一次测「50MB / 10 片，并发 5」得到 **快 2 倍**（30.97s → 15.40s），
于是据此实现了分片并发。

**那是假象**：总时长太短，带宽还没成为瓶颈。片数一多（≥20 片）
就暴露——并发 4 第 1 轮就比串行慢一倍，第 2 轮直接卡死。

**教训**：测上传吞吐必须用**生产规模**的文件（≥100MB，够跑几十秒），
且**必须做串行/并发的交替对照**，不能只测一个点。

### 教训二：先测基线，再动代码

这次应该在写任何代码之前先测：
1. 本机上行基线（到公共测速端点）
2. 目标 endpoint 的 RTT
3. 本机 → 目标 的实际上行带宽

有了 (1)(3) 的对比，「本机上行限制」在 10 分钟内就能确认，
不必先写两个版本的并发实现再逐一证伪。

### 教训三：「并发更快」的直觉在带宽受限时不成立

单条 TCP 流已经吃满上行时，并发只是**重新分配**带宽，
不会增加总量，且会引入服务端不稳定性（卡死 / 连接被断）。

## 结论与后续方向

**当前状态**：纯串行（`CHUNK_CONCURRENCY = 1`，单 worker）。
这是**正确**的实现，不是待优化的遗留。

要提速只有三条路：

| 方向 | 收益 | 代价 |
|---|---|---|
| **换上行链路** | 线性提升 | 换网络 / 换机器 / 加中转 |
| **减少传输字节** | 线性提升 | 转码压缩（改变文件内容）/ 只传增量 |
| **接受现状** | 无 | 数百 GB 按 3.3 MB/s ≈ 数十小时 |

还有一个**纯软件**的观察：串行速率本身在 1.93~3.26 MB/s 间波动（差 70%）。
可能来自 TCP 拥塞控制 / socket buffer / CIFS 读与上传争带宽。
**调优 socket buffer 或拥塞算法**有时能提升 20-40%——这是唯一
不违反「不转码」且可能有收益的方向，但需先实测再改。
