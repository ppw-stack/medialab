# 数据同步上传的带宽瓶颈（2026-11-02 实测结论）

**一句话结论**：光鸭上传速率受限于**本机上行带宽（~3 MB/s）**，
不是代码实现问题。并发上传（分片并发 / 文件并发）**换不来吞吐**，
反而会让服务端不稳定。当前实现**只能串行**。

本文记录实测数据与走过的弯路，避免以后重复踩。

## 背景

「同步刮削」任务把本地影视文件（1-1.7 GB/个）传到光鸭盘。
观察到的现象：单文件要传 5-11 分钟，速率稳定在 ~3.3 MB/s。
总剩余量数百 GB → 需要数十小时。

问题：**能不能提速？**

## 实测环境

| 项 | 值 |
|---|---|
| 客户端 | prod 容器（`ssh <别名>`，<生产机IP>） |
| 网盘 | 光鸭（`guangya`），真实账号 |
| OSS endpoint | `cn-zhangjiakou.oss.aliyuncs.com`（阿里云张家口） |
| RTT | **31 ms** |
| 分片大小 | 5 MB（`CHUNK_SIZE`） |

## 关键数据

### 1. 本机上行基线

```
本机 → speed.cloudflare.com:  3.2 MB/s
```

### 2. 本机 → 光鸭 OSS

| 分片方式 | 耗时（100MB） | 速率 |
|---|---|---|
| 1 片 × 100MB（单 PUT） | 36.4s | 2.75 MB/s |
| 20 片 × 5MB（生产方式） | 44.4s | 2.25 MB/s |
| 5 片 × 20MB | 43.8s | 2.28 MB/s |

**与本机上行 3.2 MB/s 基本吻合** → 瓶颈是本机上行，不是光鸭。

### 3. 分片大小几乎不影响速率

1 片 / 5 片 / 20 片都是 2.25-2.75 MB/s。

**这是「带宽受限」而非「RTT 受限」的决定性证据**——若是 RTT 受限，
大分片（请求数少、RTT 少）会明显更快。

### 4. 并发实测（全部无收益或更差）

**同一 uploadId 的分片并发**

| 场景 | 结果 |
|---|---|
| 100MB / 20片，串行 | 21.08s（4.74 MB/s） |
| 100MB / 20片，并发 2 | 21.32s（4.69 MB/s）——**零收益** |
| 100MB / 20片，并发 4 | 21.14s（4.73 MB/s）——**零收益** |
| 200MB / 40片，并发 4 | ❌ 卡死（>90s 无响应） |
| 纯串行 4 轮 | 24.28 / 26.89 / 25.70 / 17.08s ← 稳定 |

**不同 uploadId 的并发**（= 文件级并发）

| 场景 | 结果 |
|---|---|
| 60MB × 4，并发 4 | ❌ `Server disconnected without sending a response` |
| 20MB × 4，并发 2 | ❌ 卡死 |
| 30MB × 2，并发 2 | ok，但总吞吐 2.40 MB/s |
| 60MB × 2，并发 2 | ok（3 轮），总吞吐 2.26~2.43 MB/s |

**严格对照**（60MB × 2，生产分片路径，交替跑）

| 模式 | 耗时 | 总吞吐 |
|---|---|---|
| 串行 | 36.8s | **3.26 MB/s** |
| 并发 2 | 66.8s | 1.80 MB/s（**比串行慢 45%**） |
| 串行 | 62.1s | 1.93 MB/s |
| 并发 2 | 48.4s | 2.48 MB/s |

并发**不稳定优于串行**，且波动极大。

### 5. 小文件并发有时「看起来」有收益 —— 但不是真的

| 场景 | 结果 |
|---|---|
| 1MB × 6，并发 6（单 PUT，不分片） | ok=6 err=0，1.48x 加速 |
| 20MB 单片 × 2，并发 2 | 3.17 MB/s（接近翻倍） |
| 20MB 单片 × 4，并发 4 | ❌ 卡死 |

但小文件本来就不是瓶颈（一个 nfo 传 2-4 秒），且 ≥3 并发就会卡死。

### 6. 严格 A/B（交替 5 轮，消除时间漂移）—— 并发增益 0.96x

前面各项测试的**窗口太短**，被「并发偶尔能冲高」误导。
严格对照：**同一个 40MB 文件，单流与并发 2 交替跑 5 轮**。

| 轮次 | 单流 | 并发 2 |
|---|---|---|
| 1 | 3.26 MB/s (12s) | 3.12 MB/s (26s, ok=2) |
| 2 | 3.28 MB/s (12s) | 3.18 MB/s (25s, ok=2) |
| 3 | 3.21 MB/s (12s) | 3.04 MB/s (26s, ok=2) |
| 4 | 3.26 MB/s (12s) | 3.11 MB/s (26s, ok=2) |
| 5 | 3.23 MB/s (12s) | 3.28 MB/s (24s, ok=2) |

```
单流:   中位 3.26 MB/s   范围 3.21~3.28
并发2: 中位 3.12 MB/s   范围 3.04~3.28
→ 增益 0.96x（并发没有收益）
```

**总吞吐不变**——并发只是把同样的带宽分给两个文件，
每个文件变慢一倍，总时间一样。

### 7. 文件大小 × 并发度 矩阵

| 文件 / 分片 | 并发 1 | 并发 2 |
|---|---|---|
| 20MB / 4 片 | 1.42 / 1.99 / 1.40（中位 1.42） | 0.06 / 4.81 / 4.43（中位 4.43）❌ 首轮几乎卡死 |
| 60MB / 12 片 | 4.62 / 4.63 / 4.73（中位 **4.63**）✅ | 4.57 / 4.61 / 4.58（中位 **4.58**）✅ |
| 100MB / 20 片 | 21.08s（4.74） | 21.32s（4.69） |
| 200MB / 40 片 | 稳定 | ❌ 卡死 |

**60MB 规模下并发 1 与并发 2 完全相同**（4.63 vs 4.58）——
单流已吃满上行。生产文件 1.0~1.7 GB 落在同一区间。

### 8. 上行容量实测：单流用不满，双流可以跑满

同时上传到 OSS + 一条独立的 Cloudflare 上行流：

| 轮次 | 到 OSS | 独立流 | 合计 |
|---|---|---|---|
| 1 | 2.30 MB/s | 3.72 MB/s | **6.02 MB/s** |
| 2 | 2.78 MB/s | 3.91 MB/s | **6.69 MB/s** |
| 3 | 2.37 MB/s | 2.75 MB/s | **5.12 MB/s** |

**上行总容量约 5-6.7 MB/s**，但单流只跑到 ~3 MB/s。
瓶颈是**单流的 TCP 窗口 / 延迟×带宽积**，不是链路上行。

**但这不能用于提速**——两条流必须去**不同的服务器**才安全：
并发到**同一个 OSS** 时服务端会限流（卡死 / `Server disconnected`）。
光鸭只有一个 OSS 桶，无法把并发流分散到不同目标。

### 9. TCP 层证据（`ss -tin`，上传进行中）

到阿里云 OSS 的连接（`114.237.67.63:443`）：

```
delivery_rate = 0.83 MB/s   ← 实际交付
pacing_rate   = 7.48 MB/s   ← BBR 想跑
snd_wnd       = 523264 (511KB)  ← 窗口充足
cwnd          = 15
rtt           = 32.9ms
bytes_retrans = 0            ← 零重传
app_limited   = True         ← BBR 认为「应用没喂够」
```

**零重传 + 窗口充足 + BBR 目标远高于交付** → 不是丢包，也不是窗口不够。

### 10. 已排除的其它方向

| 方向 | 实测 | 结论 |
|---|---|---|
| 换拥塞算法（BBR→Reno） | 容器内 `sysctl` 不生效（网络命名空间独立）；宿主机改了也不影响容器视图 | 不可行 |
| 调大 `tcp_wmem`（4MB→16MB） | 同上，容器内看不到宿主机改动 | 不可行 |
| 调大 `SO_SNDBUF`（应用层 socket 选项） | 默认 3.28/3.29 MB/s vs 8MB 缓冲 3.21/3.27 MB/s —— **完全相同** | 无效 |
| 增大分片（减少 RTT 空档） | 每片额外空档只有 ~0.1-0.3s（一个 RTT）；50MB 单片 5.00 MB/s 反而最快 | 已最优 |
| 无线链路干扰 | 同机另有 5 个容器（MoviePilot / immich / Redis），但采样显示它们当时空闲；速率波动 1.4~4.8 MB/s 源于 WiFi 本身 | 不可控 |

**应用层已无可调参数**。

## 走过的弯路（方法论教训）

### 教训一：小样本测试在带宽受限的系统上会给出完全错误的结论

第一次测「50MB / 10 片，并发 5」得到 **快 2 倍**（30.97s → 15.40s），
于是据此实现了分片并发。

**那是假象**：总时长太短，带宽还没成为瓶颈。片数一多（≥20 片）
就暴露——并发 4 第 1 轮就比串行慢一倍，第 2 轮直接卡死。

**教训**：测上传吞吐必须用**生产规模**的文件（≥100MB，够跑几十秒），
且**必须做串行/并发的交替对照**，不能只测一个点。

### 教训二：先测基线，再动代码

这次应该在写任何代码之前先测：
1. 本机上行基线（到公共测速端点）
2. 目标 endpoint 的 RTT
3. 本机 → 目标 的实际上行带宽

有了 (1)(3) 的对比，「本机上行限制」在 10 分钟内就能确认，
不必先写两个版本的并发实现再逐一证伪。

### 教训三：「并发更快」的直觉在带宽受限时不成立

单条 TCP 流已经吃满上行时，并发只是**重新分配**带宽，
不会增加总量，且会引入服务端不稳定性（卡死 / 连接被断）。

### 教训四：必须做严格 A/B —— 交替多轮，不是各测一次

本次调研里，同一个「并发 2」的配置在不同测试中给出过
**1.9x 加速**、**0.96x**、**0.3x** 三种结论。差别全在测量方法：

- ❌ 各测一次 → 会被「并发偶尔冲高」的窗口误导
- ✅ **单流与并发交替跑 5 轮** → 稳定结论（0.96x）

交替能消除「链路随时间漂移」的影响（本机是 WiFi，
速率本来就在 1.4~4.8 MB/s 间波动）。

**判据**：只有当并发在**交替多轮**下都稳定优于单流，
才算真收益。一次性测试的加速都是噪声。

## 结论与后续方向

**当前状态**：纯串行（`CHUNK_CONCURRENCY = 1`，单 worker）。
这是**正确**的实现，不是待优化的遗留。

### 已排除的方向（都实测过，无收益或有害）

| 方向 | 实测结果 |
|---|---|
| 分片并发 | 零收益（21.08 vs 21.32s）或卡死 |
| 文件级并发 | 增益 0.96x；≥3 并发触发 `Server disconnected` |
| 换 TCP 拥塞算法 | 已是 BBR（最优）；容器内 sysctl 不生效 |
| 调大 `tcp_wmem` | 容器内看不到宿主机改动 |
| 调大 `SO_SNDBUF` | 3.28 vs 3.21 MB/s —— 无差异 |
| 增大分片减少 RTT 空档 | 空档仅 ~0.1-0.3s/片；50MB 单片反而最快 |

### 真正的原因

- 本机是 **WiFi**（wlan0，5GHz，协商 432 Mbit/s），速率随信道占用在
  **1.4~4.8 MB/s** 间波动（同机另有 5 个容器共享该链路）
- 单流只跑到 ~3 MB/s，而**双流到不同服务器可跑到 5-6.7 MB/s**
  → 单流受限，但光鸭只有**一个 OSS 桶**，并发流无法分散到不同目标
- 到 OSS 的连接 `app_limited=True` + **零重传** + 窗口充足
  → 服务端接收侧在限速，客户端侧已无可调空间

### 要提速，只有三条路

| 方向 | 收益 | 代价 |
|---|---|---|
| **换上行链路**（有线 / 云服务器） | 线性提升，且单流就能跑满 | 换网络 / 换机器 / 加中转 |
| **减少传输字节** | 线性提升 | 转码压缩（改变文件内容）/ 只传增量 |
| **接受现状** | 无 | 数百 GB 按 3.3 MB/s ≈ 数十小时 |

**结论：应用层已无优化空间。** 唯一的软件侧前提是「换一个上行更宽的
网络环境」——同一份代码在有线/云服务器上，速率会成倍提升。
