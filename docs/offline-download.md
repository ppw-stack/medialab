# 离线下载（本地 → 光鸭）：可行性实测结论

> 2026-11-04。真实账号、真实文件、真实公网入口。

**一句话结论**：**技术上完全可行**（文件能完整落地光鸭、md5 一致），但
**实测速率只有 ~0.75 MB/s，比直传的 3.3 MB/s 慢 4.4 倍**——瓶颈不在
你的链路，在光鸭下载器对**随机分片**的重试策略。

## 背景

「数据同步」是 `128 → 光鸭 OSS` 的**上行**，实测受本机上行带宽限制
（~3.3 MB/s，几百 GB 要数十小时，见 `upload-bandwidth.md`）。

光鸭的**离线下载**反过来：光鸭服务器拿着 URL 主动来拉。流量方向是
**下行**，本机只承担接收 → 上行需求 ≈ 0。

## 实测数据（生产环境，真实账号）

### 环境

| 项 | 值 |
|---|---|
| 客户端 | prod 容器（`ssh mp`，192.168.0.128） |
| 公网入口 | `http://home.banstack.top:8092`（端口映射到容器 8080） |
| 源文件 | 172 的 CIFS 共享（`WATCH_DIR`） |
| 网盘 | 光鸭（`guangya`），真实账号 |
| 被测文件 | 2.33 GB（星际迷航 2009 1080p）/ 5 MB（测试件） |

### 各环节速率

| 环节 | 速率 |
|---|---|
| 128 内网直读 CIFS 文件 | **2.6 GB/s** |
| 128 内网经 HTTP 服务读 | **626 MB/s** |
| **公网入口单个 100MB 分片** | **17.2 MB/s** |
| **公网入口单个 8MB 分片** | 2.2~3.5 MB/s |
| **光鸭实际拉取速度** | **~0.75 MB/s** ❌ |

**链路不是瓶颈**（17.2 MB/s），**服务实现不是瓶颈**（626 MB/s）。

### 光鸭的分片行为

光鸭把文件切成**变长的随机区间**并**并发拉取**，实测：

| 观察 | 数据 |
|---|---|
| 分片大小 | 最小 0.02MB / 中位 5.75MB / 最大 50MB / 平均 5.16MB |
| Range 起点步长 | 中位 1.1 MB（**变长**，不是固定块） |
| **重复拉取比例** | **73%**（2.3GB 文件总拉 2242MB，去重后仅 429MB） |
| 5MB 小文件 | 同一区间被拉 **130 次** |
| 2.3GB 大文件 | 65 分钟拉完，重复区间最多被拉 10 次 |

「同一秒同一区间 3 次请求」——是光鸭的**多下载节点并行 + 重试**，
不是服务端问题（我方无连接中断、无 broken pipe，响应 206 + Content-Range
完全正确）。

## 踩到的坑（都已在代码里修掉）

### ① 光鸭会发 `HEAD` 请求

不支持 → `405 Method Not Allowed` → **任务可能直接失败**。

必须同时注册 `@router.head`。

### ② 光鸭有两条路径的 URL 编码方式不同

- 正常路径：`%E7%94%B5`（单次编码）—— 我提交的形式
- 重试路径：`%25E7%2594%25B5`（**双重编码**）—— 光鸭自己又编码了一遍 `%`

双重编码的那批请求原本**全部 403**（token 校验失败）。
解法：服务端**再 `unquote` 一次**（`unquote` 幂等，普通编码不受影响）。

### ③ 模块级 `APIRouter` 不能复用

`router` 若是模块级全局对象，多次 `include_router` 到不同 app 时，
路由会绑在**第一次**的 app 上（后挂的 app 拿不到）——测试里尤其明显
（单跑通过、连跑失败）。**必须在 `mount_offline_files()` 内部新建**。

### ④ 光鸭的 `progress` 字段不是可靠的百分比

小文件实测 `progress` 37→95→97（确实接近百分比）；
但 2.3GB 文件下载到 88% 时 `progress` 只有 4。

**判据**：不要用 `progress` 判定完成。**等任务从活跃列表消失** +
**以「目标目录出现同名同大小文件」为准**（光鸭的目录索引有延迟，验早了
会误报）。

> ⚠️ 迁移功能（115→光鸭）把 `progress` 当百分比显示
> （`migration.py` 的 `_progress_text`）——**那个显示是错的**，
> 大文件时会显示个位数。本次未改（不在任务范围内），但别学它。

### ⑤ FastAPI 不支持运行时增删路由 → 配置页面上改、**路由常驻**

三项配置（`OFFLINE_HMAC_SECRET` / `OFFLINE_PUBLIC_BASE` / `OFFLINE_FILES_ROOT`）
原本只能改 `.env.prod` 重启容器。现在它们落在 `app_env_settings` 表，
在**「离线下载」页的配置区改完立即生效**（不用重启）。

但 FastAPI 不能运行时增删路由——所以 `mount_offline_files()` **无条件
挂载**，由每次请求时读当前配置决定放行：三项没配齐 → **403**（不暴露
任何文件，比 SPA 兜底吞掉更诚实）。

### ⑥ 目录浏览不限权（用户明确要求）

源目录浏览能列服务能看到的**任何目录**——与「数据同步」的
`/upload-tasks/local-dirs` 一致（面板本身已是管理员权限）。暴露面靠
「没配齐不暴露文件」控制，而非目录白名单。

### ⑦ 密钥永不回显、不进日志（2026-11-04 加入）

- API 只返回 `has_secret: true/false`，不返回密钥值
- 「保存配置」时密钥留空 = **不修改**（不能用「空串 = 清除」语义——
  密钥永不回显，用户没法区分「已配置」与「想清空」）
- 启动期初始化日志只打 key 与 `<set>` 占位（`test_init_log_never_leaks_secret`）

### ⑧ URL 路径基准是**源根目录**，不是源目录（2026-11-04 prod 事故）

`build_url` 的路径、token 都以**源根目录**（`files_root`）为基准——文件
服务收到请求后按它解析路径并验 token。源目录（`local_root`）只是「从哪
开始扫」；它是源根目录的**子目录**时，若 URL 用相对 local_root 的路径，
中间段缺失 → 光鸭来拉**全部 404**。此前所有测试恰好都从源根目录开跑，
两者相等，问题被掩盖到 prod。

防线：`OfflineParams.files_root` 随任务下发；提交时（API 400）与执行时
（任务失败并写明原因）双重校验 `local_root` 必须在源根目录之下。

### ⑨ BT/磁力推送：**不可行**——光鸭磁力只查自家种子库（2026-11-04 实验结论）

四轮对照实验（真实生产环境）：

| 提交物 | 结果 |
|---|---|
| 裸磁力（纯 infohash） | ❌ 秒拒「BT文件不存在」 |
| `.torrent` 文件的 http URL | ❌ 当**普通文件**下载（拉的是种子文件本体，不解析内容） |
| 磁力 + 8 个公共 tracker（Sintel，全网知名种子） | ✅ **接受并下载**（20 秒完 129MB，BT 引擎正常） |
| 磁力 + 自建 tracker（自制 1MB 种子 + qB 活跃做种 + tracker 注册确认） | ❌ **秒拒同款错误** |

结论：光鸭的磁力处理 = **在自家种子库里查 infohash**，不查外部 tracker、
不从 peer 解析元数据（BEP 9）。知名种子在库里所以「支持磁力」，
自制/私有内容一律不存在。**自建 tracker 无法让本地文件经 BT 进光鸭**。

副产品（保留可用）：阿里云 opentracker 容器（`47.117.113.250:6969`，
防火墙已开 TCP+UDP）+ qB 做种验证通过——**BT 分发链路本身是通的**，
可用于给朋友/多设备分发本地文件（磁力 → 他们下载），只是光鸭不在此列。

⚠️ 实验还发现：光鸭 BT 任务会**先落 `来自：云添加` 目录再复制到目标
目录**（两处各一份），产品化清理时两处都要管。

本地文件进光鸭的可行路径：**HTTP 离线下载**（本文件主题）或**数据同步
直传**（3.3MB/s 更稳）。

## 结论

| | 直传（现有「数据同步」） | 离线下载（本次） |
|---|---|---|
| 方向 | 上行 3.3 MB/s | 下行 17.2 MB/s（链路能力） |
| **实际达成** | **3.3 MB/s** | **0.75 MB/s** ❌ |
| 复杂度 | 低 | 高（HTTP 服务 + HMAC + 轮询） |
| 公网暴露 | 无 | 有（需临时开端口映射） |

**离线下载在这个场景下不划算**——光鸭下载器的分片重试把 17.2 MB/s 的
链路能力浪费掉了 95%。

**它什么时候才划算**：源文件**本来就在大带宽 CDN 上**（如 115 直链），
且光鸭拉 CDN 的效率高——那正是**迁移功能**（115→光鸭）的场景。
「本地 → 光鸭」用离线下载反而更慢。

**如果一定要用本地文件走离线下载**，可行的优化方向（未验证）：
- 让服务支持**更大的分片**（但光鸭的切分策略由服务端决定，客户端不可控）
- 换公网入口（链路已是 17.2 MB/s，瓶颈不在这，换了也白换）

## 扫描是流水线，不是先扫完再传（2026-11-04 加入）

`run_offline_download` 是**生产者-消费者**结构：扫描在工作线程里走目录
树（CIFS 的 readdir/stat 是阻塞 IO，不能占事件循环），每找到一个文件就
丢进 `asyncio.Queue`，工作协程立刻提交——**第一个文件的提交在扫描开始
后毫秒级发生**，不用等整棵树扫完。「已发现」计数随扫描实时增长。

哨兵（`_WALK_DONE`）收尾：工作协程每消费一次哨兵就把它传给下一个，
**最后一个消费者不再回填**——否则队列的 unfinished 计数永远归不了零，
`queue.join()` 会挂死。

## 下载成功后删除本地文件（2026-11-04 加入）

参数 `delete_after_upload`（前端「下载后删本地」开关，打开时**二次确认**）。

与「数据同步」**同一套机制**（`app/services/upload_cleanup.py`），
三重保护一致：

1. 只对**云端确认落盘**的文件删（目标目录出现同名同大小才算）
2. 路径安全：普通文件 / 非隐藏 / 在**用户选的源目录**内
3. 空目录一并删掉（向上递归 `os.rmdir`，源目录本身保留）

**与数据同步的唯一差异**：直传上传完文件**已在云端**，立即校验；离线
下载提交任务后文件**还没到**，要等「任务结束 + 校验落盘」才删。
删除失败只记日志，不翻转结果（下载已成功）。
