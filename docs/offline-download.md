# 离线下载（本地 → 光鸭）：可行性实测结论

> 2026-11-04。真实账号、真实文件、真实公网入口。

**一句话结论**：**技术上完全可行**（文件能完整落地光鸭、md5 一致），但
**实测速率只有 ~0.75 MB/s，比直传的 3.3 MB/s 慢 4.4 倍**——瓶颈不在
你的链路，在光鸭下载器对**随机分片**的重试策略。

## 背景

「数据同步」是 `128 → 光鸭 OSS` 的**上行**，实测受本机上行带宽限制
（~3.3 MB/s，几百 GB 要数十小时，见 `upload-bandwidth.md`）。

光鸭的**离线下载**反过来：光鸭服务器拿着 URL 主动来拉。流量方向是
**下行**，本机只承担接收 → 上行需求 ≈ 0。

## 实测数据（生产环境，真实账号）

### 环境

| 项 | 值 |
|---|---|
| 客户端 | prod 容器（`ssh mp`，192.168.0.128） |
| 公网入口 | `http://home.banstack.top:8092`（端口映射到容器 8080） |
| 源文件 | 172 的 CIFS 共享（`WATCH_DIR`） |
| 网盘 | 光鸭（`guangya`），真实账号 |
| 被测文件 | 2.33 GB（星际迷航 2009 1080p）/ 5 MB（测试件） |

### 各环节速率

| 环节 | 速率 |
|---|---|
| 128 内网直读 CIFS 文件 | **2.6 GB/s** |
| 128 内网经 HTTP 服务读 | **626 MB/s** |
| **公网入口单个 100MB 分片** | **17.2 MB/s** |
| **公网入口单个 8MB 分片** | 2.2~3.5 MB/s |
| **光鸭实际拉取速度** | **~0.75 MB/s** ❌ |

**链路不是瓶颈**（17.2 MB/s），**服务实现不是瓶颈**（626 MB/s）。

### 光鸭的分片行为

光鸭把文件切成**变长的随机区间**并**并发拉取**，实测：

| 观察 | 数据 |
|---|---|
| 分片大小 | 最小 0.02MB / 中位 5.75MB / 最大 50MB / 平均 5.16MB |
| Range 起点步长 | 中位 1.1 MB（**变长**，不是固定块） |
| **重复拉取比例** | **73%**（2.3GB 文件总拉 2242MB，去重后仅 429MB） |
| 5MB 小文件 | 同一区间被拉 **130 次** |
| 2.3GB 大文件 | 65 分钟拉完，重复区间最多被拉 10 次 |

「同一秒同一区间 3 次请求」——是光鸭的**多下载节点并行 + 重试**，
不是服务端问题（我方无连接中断、无 broken pipe，响应 206 + Content-Range
完全正确）。

## 踩到的坑（都已在代码里修掉）

### ① 光鸭会发 `HEAD` 请求

不支持 → `405 Method Not Allowed` → **任务可能直接失败**。

必须同时注册 `@router.head`。

### ② 光鸭有两条路径的 URL 编码方式不同

- 正常路径：`%E7%94%B5`（单次编码）—— 我提交的形式
- 重试路径：`%25E7%2594%25B5`（**双重编码**）—— 光鸭自己又编码了一遍 `%`

双重编码的那批请求原本**全部 403**（token 校验失败）。
解法：服务端**再 `unquote` 一次**（`unquote` 幂等，普通编码不受影响）。

### ③ 模块级 `APIRouter` 不能复用

`router` 若是模块级全局对象，多次 `include_router` 到不同 app 时，
路由会绑在**第一次**的 app 上（后挂的 app 拿不到）——测试里尤其明显
（单跑通过、连跑失败）。**必须在 `mount_offline_files()` 内部新建**。

### ④ 光鸭的 `progress` 字段不是可靠的百分比

小文件实测 `progress` 37→95→97（确实接近百分比）；
但 2.3GB 文件下载到 88% 时 `progress` 只有 4。

**判据**：不要用 `progress` 判定完成。**等任务从活跃列表消失** +
**以「目标目录出现同名同大小文件」为准**（光鸭的目录索引有延迟，验早了
会误报）。

> ⚠️ 迁移功能（115→光鸭）把 `progress` 当百分比显示
> （`migration.py` 的 `_progress_text`）——**那个显示是错的**，
> 大文件时会显示个位数。本次未改（不在任务范围内），但别学它。

## 结论

| | 直传（现有「数据同步」） | 离线下载（本次） |
|---|---|---|
| 方向 | 上行 3.3 MB/s | 下行 17.2 MB/s（链路能力） |
| **实际达成** | **3.3 MB/s** | **0.75 MB/s** ❌ |
| 复杂度 | 低 | 高（HTTP 服务 + HMAC + 轮询） |
| 公网暴露 | 无 | 有（需临时开端口映射） |

**离线下载在这个场景下不划算**——光鸭下载器的分片重试把 17.2 MB/s 的
链路能力浪费掉了 95%。

**它什么时候才划算**：源文件**本来就在大带宽 CDN 上**（如 115 直链），
且光鸭拉 CDN 的效率高——那正是**迁移功能**（115→光鸭）的场景。
「本地 → 光鸭」用离线下载反而更慢。

**如果一定要用本地文件走离线下载**，可行的优化方向（未验证）：
- 让服务支持**更大的分片**（但光鸭的切分策略由服务端决定，客户端不可控）
- 换公网入口（链路已是 17.2 MB/s，瓶颈不在这，换了也白换）
